**一句话定义**：程序持续监测流量与受管网络方案，关键保护异常时客户端立即阻断并报告；后台处理托管问题，AI 只读辅助诊断；每两小时只读归档，每天按到期规则生成包含用量、Claude 出口审计与应急处置的统一日报。

**完整处理链**：监测事实 → 识别异常 → 按预授权紧急保护 → 通知与上报 → 诊断及受控修复 → 实际复查 → 记录恢复；归档与日报独立保存证据，不代替即时保护。

**阅读约定**：区分“用户提供的现行规程”“本轮确认的产品增量”“仍待验证的实现参数”。现行脚本未在本轮取得或执行；分类、样例数字和调度要求不得被当作新应用已实现的证明。引用编号见第 13 节。

## 1. 产品目标、范围与既有文档衔接

### 1.1 产品目标

让普通用户在日常使用中知道流量花在哪里、是否遵守所选网络方案、是否发生异常、应用采取了什么保护，以及还有什么需要处理。正常时少打扰，危急时立即保护和报告，不要求用户盯日志或理解代理参数。[U1—U3]

第四板块同时覆盖实时运行、证据留存与每日审计。它不新建代理内核、另一套网络配置入口或配额账本；FD-02 提供必要检测与复查，FD-03 提供受管路由、保护执行、后台资源和服务端额度能力。

### 1.2 包含与不包含

| 范围 | 本份规定 |
|---|---|
| 本机流量 | 实时上传／下载、连接、代理／直连、可识别应用与出口 A／B 的分布、历史趋势及缺测说明 |
| 用户月度额度 | 展示和引用 FD-03 的服务端用户账目与同步状态，不另算或改写配额 |
| 路由与保护监测 | 对照事件发生时有效的方案、规则和出口分工，识别异常与证据缺口 |
| 紧急保护 | 在预授权内由客户端程序执行受支持的阻断，回读效果并立即通知、上报 |
| 诊断与恢复 | 后台处理资源与模板问题；AI 只读分析；调用同一受管执行能力修复并复查 |
| 归档与日报 | 两小时只读归档、SHA-256 去重与核验、当地 09:00 后首次可用唤醒补做日报、双格式交付 |
| 本地与后台信息范围 | 本地明细；后台默认汇总和最小事件状态；进一步诊断包经用户授权提交 |
| 文件、Cookie 和账号清理 | 仍归 FD-01；监测或修复不附带清理账号、项目资料 |
| 账号风控判定、解密对话、秘密采集 | 不建设；不根据路由成功推断账号状态，不采集加密载荷内容 |
| 全盘删除、历史报告改写 | 归档／审计禁止删除文件或改写历史报告；生命周期清理另行约定 |
| 无时延、零泄漏、全机覆盖保证 | 不作未验证承诺；响应时间、实际覆盖及失败情况均需说明 |

### 1.3 对已有边界的局部补充

| 原有要求 | 本轮确认的增量 |
|---|---|
| 原监控任务只报告、不整改 | 原只读归档／审计职责保留；产品新增由 FD-03 受管执行能力承担的实时紧急保护，不把旧脚本改成万能修复脚本 |
| FD-02 修改前确认 | 首次启用可预授权指定危险条件下的紧急阻断；超出维护范围的新修复仍需具体确认 |
| FD-03 托管维护与额度 | 本模块观察、解释和展示其结果；不以监测创建第二配置源、不以本机用量覆盖服务端账目 |
| FD-01 缓存与日志可清理 | 活动日志、当前审计窗口证据和已生成日报不进入普通默认清理；另行明确保留与用户主动清理规则 |
| 每日“完整成功报告” | 产品口径明确为生成完整有效的报告，不是仅结论为 PASS；FAIL 和不完整监控结论也算已交付 |
| 单一审计结论 | 路由结论和覆盖状态分别记录；已有错误出口不能被覆盖不完整掩盖 |

本份不修改前三份原文件，仅记录以上衔接规则。用户项目保护、正常登录资料保留、无聊天框、固定出口不静默改变及配额约束继续有效。[FD01 §2—3、§9；FD02 §5—8；FD03 §1、§7—10]

## 2. 已确定的核心产品规则

| 编号 | 规则 |
|---|---|
| R01 | 监测、紧急保护、归档和日报属于同一应用的协作能力，不再建设独立 Clash 控制面。 |
| R02 | 已确认 WRONG_ROUTE 或破坏 Claude 出口约束的关键保护异常，客户端立即启动预授权保护并报告，不等两小时归档或日报。 |
| R03 | 第一响应由客户端程序完成，不依赖 AI、后台在线或上报成功；不以停止 Clash／TUN 本身代替有效保护。 |
| R04 | 阻断指令发出、已确认生效、失败或未确认必须分开；断开现有错误连接还须防止再次错误连接。 |
| R05 | 后台管理事件、模板和资源，客户端负责实际执行与反馈；后台发布成功不等于用户端修复成功。 |
| R06 | AI 只读分析脱敏证据并建议修复；不拥有任意管理员终端、不自行解除保护或换出口。 |
| R07 | 紧急阻断按首次启用的范围授权执行；新修复、复测和恢复分别遵循既有明确授权边界。 |
| R08 | 正确固定链的连接错误、预期拒绝和错误路线分别分类，不将超时一律判成泄漏。 |
| R09 | 日常白名单直连、Claude 单 IP 与双 IP 分工分别按 FD-03 判定；用事件发生时的方案，不用今日配置重判旧记录。 |
| R10 | 日志不可读或覆盖不完整立即报告；无日志不等于无流量、无泄漏或保护已失效。 |
| R11 | 每两小时是归档节奏，不是应急反应时限，也不是完整日志覆盖保证。 |
| R12 | 时间与日期目录按 America/Los_Angeles 解释；日报当地 09:00 后到期，首次可用唤醒补做，不承诺准点。 |
| R13 | 归档不改、不删源日志；原始内容按 SHA-256 去重，latest 日志使用时间戳快照，归档后核验。 |
| R14 | daily_audit.due=true 时继续当日审计，不因当前小时不等于 09 跳过；执行前再次检查是否已有完整日报。 |
| R15 | 当天两份完整有效非空日报已存在则不重复生成，非 PASS 结论也算已交付；不追溯伪造漏跑日期。 |
| R16 | 日报采用左闭右开窗口，归档和当前源日志合并、按文件及规范化记录去重，重复快照不累加成流量或事件。 |
| R17 | 旧 classification_version=2 原口径保留；产品化适配须有独立可追溯版本，不改旧定义或历史报告。 |
| R18 | 归档、回放、每日审计共用分类器；AI 不临时重写过滤、分类或统计逻辑。 |
| R19 | 日报包含本机流量、服务端额度快照、Claude 路由、紧急处置、证据覆盖与诊断待办。 |
| R20 | 字节用量来自实际计量，不从日志条数推算；本机明细不冒充用户全部设备用量，缺数据不填零。 |
| R21 | PASS_ROUTE 只说明该条记录的路由与错误情况，不代表应用层成功、整机无绕行或账号正常。 |
| R22 | WRONG_ROUTE>0 保留 FAIL；覆盖不足同时显示 MONITORING_INCOMPLETE，后续修好不抹掉窗口内事件。 |
| R23 | 完整明细默认留本地；后台只收用量汇总、最小事件与处置状态，更多证据须经授权且脱敏。 |
| R24 | 归档／审计只读，不启动 Claude／浏览器、不发测试请求、不改网、不删文件、不复制认证材料。 |
| R25 | 源日志意外含秘密时作为异常处理，不把凭据原样复制到普通归档；不把脱敏副本声称为原始字节一致。 |
| R26 | 暂不增加独立“流量安全分”；沿用问题等级，需完整重新评估时调用 FD-02。 |

## 3. 运行分工与三层执行频率

### 3.1 三层运行安排

| 层次 | 时机 | 产物与边界 |
|---|---|---|
| 实时监测与保护 | 应用运行期间持续观察，按事件或经验证的短周期检查 | 即时状态、事件、阻断及通知回执；不等待归档和日报 |
| 只读增量归档 | 计划每 2 小时运行一次 | 原始日志归档、快照、哈希、归档结果、即时异常线索与 daily_audit 到期状态 |
| 每日审计 | 当地 09:00 起到期，之后首次可用唤醒执行 | daily-audit.md 与 daily-audit.json；完整窗口统计、流量、处置和证据边界 |

机器睡眠、应用未运行或任务没有唤醒时不保证准点。报告列出实际运行与覆盖，不能以计划周期替代真实执行证据。实时监测不得将“每两小时归档一次”理解为每两小时才检查危险条件。

### 3.2 职责与权限

| 责任方 | 承担职责 | 不取得的权限 |
|---|---|---|
| 客户端采集／分类 | 读取运行状态、流量和日志；形成结构化事实、发现异常 | 不凭文字猜测账号或明文内容，不创建另一套自由配置 |
| 客户端受管执行能力 | 预授权紧急阻断；执行已批准恢复或用户确认修复；回读效果 | 不换未知节点、不关闭保护来恢复联网、不扩大到未授权对象 |
| 只读归档／每日审计 | 复制合规日志、去重、哈希验证、回放、生成报告 | 不调用改网能力、不运行测试流量、不删源或历史报告 |
| 管理后台 | 接收事件、核查托管资源与模板、发布修正、跟踪实际结果 | 不以服务端停代理代替本机保护，不默认收集完整浏览历史 |
| AI 诊断 | 关联证据、解释异常、提出可验证的原因与受支持动作 | 不直接实施应急、不改计数、账目、分类规则或历史文件 |

模型服务配置在本应用服务端，提示词在客户端。归档和标准日报由程序离线完成；独立 AI 任务经数据授权发送脱敏汇总、生成每日分析，不向归档任务赋予联网权限。网络修复另走已确认工具清单，AI 不决定紧急阻断或修改账目。

### 3.3 一体化用户流程

首次启用时说明监测内容、后台上报范围及紧急保护影响，取得相应授权。日常展示当前方案、速率、用量和保护状态；普通明细折叠。事件发生后先保护、通知，再进入诊断和受控处理；恢复后在同一事件中记录复查结果。

主动联网复测与故障演练由 FD-02 按授权执行，产物可进入事件及日报；归档／审计本身不得为了补证据启动客户端、制造请求或执行演练。后台上报走预先批准的控制路径，不能在应急时临时增加宽泛直连。

## 4. 流量、方案运行与异常监测

### 4.1 实时流量和分布

| 检测面 | 用户可见结果 |
|---|---|
| 当前传输 | 上传／下载速率、活动连接、数据更新时间和采集状态 |
| 本机统计 | 今日或所选窗口的上传＋下载、代理／直连、可识别应用用量 |
| 出口统计 | 单 IP 汇总；双 IP 展开 A／B，说明角色与事件时生效方案 |
| 环境归属 | 本机、WSL、已支持客体及设备引用；不能将一端结果冒充全用户范围 |
| 服务端额度 | FD-03 用户月用量、剩余量、重置时间、单位和最近同步时间 |
| 历史变化 | 用量趋势、异常增长、出口和配置变化的时间线；无历史则不称长期稳定 |

只有来源可靠的应用、域名与连接归属才分类；无法确定的显示“来源未识别”。按路线 A／B 统计与按应用统计不是同一概念，不能将出口 A 的全部字节无条件称作 Claude 用量。

### 4.2 本机观测与配额账目分离

本机字节数据用于解释这台设备的流量分布；后台月度配额沿用 FD-03 的权威来源、计量点和单位。允许多端时，用户总量包含其他设备；同步延迟、协议开销或采样差异如实说明，不强行改成一致。[FD03 §7—8]

双 IP 与获准多端额度合计、前置代理与固定出口两段不重复向用户扣量；重启、重装或恢复本地配置不重置服务端账目，均沿用 FD-03。

不从路由日志记录数推算 GB，不把“没有采集到”填成零。日常白名单真正直连以及本机／局域网通信不计入代理额度；Claude 专用模式中同样的目标若实际走代理，应按实际路线计量。

新增采集须识别内核重启、计数重置、重复样本和缺测时段。具体采样频率、累计方法与容许误差留待验证；日报保留数据来源和可用覆盖，不能把每次取得的累计值直接相加。

### 4.3 监测按当时方案判定

| 当时方案 | 正常预期 | 需要调查的偏离 |
|---|---|---|
| 日常单 IP | Claude 用 A；批准的普通白名单直连；其他代理业务用 A | Claude 被直连放行，或应代理的普通目标未经批准直连 |
| Claude 单 IP | 已声明公网范围由 TUN 接管并走 A；基础例外按模板 | 受控连接使用未批准出口，或保护约束失效 |
| Claude 双 IP | Claude 用 A；其他普通公网业务用 B；必要例外明确 | Claude 转入 B／普通组／直连，或其他实际违反 A／B 分工的行为 |

方案切换、后台更新与用户白名单修改应留下版本和生效时间。正常授权变化与意外漂移分别记录；不能仅因为看到了 DIRECT 或 TUN 正在运行，就统一判定故障或安全。

### 4.4 异常通知

监测包括规则偏离、非预期出口变化、固定链路错误、保护状态异常、配置更新失败、用量异常增长、配额或资源状态变化，以及采集／归档异常。阈值按后续规则版本明确，不让模型临时决定统计门槛。

同一持续故障引发多条失败时归并为一个事件，保留首次、最后时间与次数；不重复弹出大量相同通知。正常归档与无须处理的状态不反复打扰，危急事件不受静默归档抑制。

|---|---|---|
| PASS_ROUTE | 无连接错误的 using CLAUDE-FIXED[COX-Fixed-Chain] 或 dial CLAUDE-FIXED | 记录中选中批准的路线，且该条未识别连接错误；不是应用层成功 |
| SAFE_REJECT | using REJECT | 明确拒绝行为；需要结合当时规则解释是否属于预期保护 |
| WRONG_ROUTE | Claude 相关流量命中 GENERAL-EGRESS、DEV-FIXED、DIRECT、GLOBAL、Emergency-Proxy 或其他非 CLAUDE-FIXED 出口 | 选中不符合当时批准方案的路线；不要求证明载荷已成功发送才报告 |
| ROUTE_ERROR | CLAUDE-FIXED／COX-Fixed-Chain 的拨号、超时、closed network 等错误 | 路线正确但固定链健康异常，不当成错误出口 |

先识别实际所选出口，再判断正确固定链的连接错误。带 error／timeout／closed network 等失败信息的 dial CLAUDE-FIXED 记为 ROUTE_ERROR，不能计入 PASS_ROUTE。解析不足或路线不可判的记录保留为核验／覆盖问题，不能为凑齐计数补成通过。

### 5.3 产品化适配，不改旧口径

新应用按照事件时间对应的用户、环境、方案版本、代理组与出口 A／B 判定批准路线，不将个人节点名称写死成所有用户的唯一正确值。旧记录继续按声明版本回放；产品适配须登记新的分类版本和映射，不覆盖 classification_version=2 的定义与历史报告。[U3]

现行规程将 chrome.exe 纳入 Claude 范围，这是个人基线。产品面向一般共享浏览器时，应区分受管专用浏览器与普通浏览器连接，不自动将全部 Chrome 流量归为 Claude；实际识别方法与支持范围需验证。更新进程路径或新增子进程也必须复查覆盖。

### 5.4 同一分类器与回放入口

材料指定 archive-run.ps1 与每日审计共用 route-classifier.ps1；按选定窗口调用 replay-logs.ps1 -WindowStartIso <起点> -WindowEndIso <终点>，使用其 counts、coverage、claude_old_process、anomalies、source_files 和 issues 生成报告。

原 v1.0 整理时未获得脚本。本轮 v1.2 已读取 archive-run.ps1、replay-logs.ps1、route-classifier.ps1，并通过旧 v2 的八条合成分类回归；这不代表新产品已接入或实时日志已验收。已确认需要适配产品 A/B 映射、报告有效性校验和并列状态；若迁移语言或运行形态，保持一个权威分类实现，以同一组样例验证。AI 不临时另写过滤器、另算计数或修改版本。

历史回放是只读证据工作，不能由它直接调用改网接口。发现新归档中的 WRONG_ROUTE 必须立即报告；当前保护是否需要阻断由实时保护职责按当前触发条件与授权处理，避免把回放当成任意执行入口。

## 6. 紧急阻断、上报、修复与恢复

### 6.1 应急触发与分级

| 事件 | 第一响应 | 后续处理 |
|---|---|---|
| 已确认当前受控连接 WRONG_ROUTE | 危急；客户端立即启动预授权阻断、保全必要事件、通知并上报 | 判断原因，修复批准配置，实际复查后恢复 |
| 关键规则／保护明确失效 | 按破坏 Claude 出口约束的程度紧急保护，不等首次错误连接 | 补齐或恢复受管保护；确认真实覆盖 |
| ROUTE_ERROR | 记录链路健康异常，保留既有保护；持续／严重故障按规则升级 | 分析前置、固定出口、资源或配置原因，不以换未知出口解围 |
| SAFE_REJECT | 记录拒绝及其规则背景，预期拒绝不刷成危急 | 若影响使用，进入普通诊断，不擅自放开 |
| 日志不可读／归档失败／覆盖不足 | 立即报告监控异常，不自动判定已泄漏 | 若同时无法确认关键保护有效，按预授权暂停相应受控连接；否则继续核查证据缺口 |
| 用量、到期或后台状态变化 | 解释 FD-03 的实际状态和既有控制结果 | 不重建限额执行逻辑，不绕过额度或服务暂停 |

危急／重要／轻度用于用户可理解的优先级；分类名称描述证据类型。仅疑似错误不能伪称已发生泄漏，普通规则提示也不一律切断全机网络。

### 6.2 第一响应由客户端程序承担

默认保护目标是受影响的受控连接与环境，阻止当前错误连接及再次错误连接；具体可实现的粒度和覆盖必须验证。需要扩大到更大作用范围时必须处于已经说明的保护授权内，不静默影响其他用户工作。

阻断不等待后台响应、AI 推理或日志归档完成。通知与证据记录不能阻塞应急执行。仅停止内核、关闭 TUN 或调用关闭连接接口，不等于已经建立防止绕行的保护；效果必须回读验证。不能承诺追回已经发生的传输或保证响应前没有任何数据离开。

记录“指令已发出”“阻断已确认”“阻断失败／未确认”，用户看到的状态以实际证据为准。阻断失败立即醒目报告，不显示“已安全”。具体响应时延与验证方式列为实现待定。

### 6.3 首次授权与后续修复

首次启用网络保护时说明并确认：在预设危险条件下，应用可以自动暂停对应网络连接、保存必要事件并向后台报告。该授权只覆盖明确对象、动作和范围，不等于后台或 AI 可任意修改电脑。

恢复已验证且仍有效的受管配置，可以纳入已批准自动维护；未知问题的新修改、变更出口 A、地区或保护边界，继续按 FD-02／FD-03 的规则确认。认证资料与项目内容不因应急而清理。[FD03 §6、§9]

### 6.4 后台、AI 与实际执行

后台核查是否为模板、订阅、前置资源或固定出口问题，发布适用修正并跟踪每个客户端结果；服务端暂停代理不是本机防直连的替代。后台只能通过受管发布与支持动作协调处理，不能借事件上报取得无限远控权限。

AI 读取脱敏事实、有效配置摘要与相关时间线，给出可确认原因、推断和建议。无 AI 时仍可阻断、归档、生成标准报告、执行已授权恢复；诊断晚到不改变先前证据与计数。

### 6.5 恢复条件与事件记录

应用修正 → 回读配置和保护 → 通过 FD-02 对相应客户端／环境复查 → 在仍获授权且资源有效时恢复。未验证、修复失败或资源不满足时保持对应保护并解释原因，不能解除保护以制造联网成功。

每个事件保留发现、阻断请求、阻断确认或失败、通知、上报尝试与确认、方案发布、客户端应用、复查和恢复的实际时间与结果；没发生的步骤留为未完成，不补造时间。

同一事件的实时通知、后台事件和日报通过同一事件引用关联。后台离线时本地待报，恢复联系后补报，不重复生成多起事故。日报保留事件发生事实，即使当日已经修好，也不能把 WRONG_ROUTE 从窗口内删除。

## 7. 每两小时只读归档

### 7.1 继承的路径与产品路径

用户现行日志来源为 %APPDATA% 下 Clash Verge Rev 的 logs/service；现行工作目录为其本地 clash-log-monitor。为便于开源，本文件将个人绝对目录表示为 %MONITOR_ROOT%，不复制用户名和私人工作目录。[M0]

```text
%APPDATA%/io.github.clash-verge-rev.clash-verge-rev/logs/service/
%MONITOR_ROOT%/YYYY-MM-DD/raw/
%MONITOR_ROOT%/YYYY-MM-DD/daily-audit.md
%MONITOR_ROOT%/YYYY-MM-DD/daily-audit.json
```

以上是现行规程的来源追溯，不是产品必须依赖外部 Clash Verge 的目录。新应用读取自己内置 Clash／受支持系统证据的实际来源，目录可迁移，审计语义不变。时间和日期目录统一按 America/Los_Angeles 解释。

### 7.2 每次执行顺序

1. 只读枚举本次可见日志，记录来源、读取状态与本次归档时间。
2. 将允许归档的原始日志按 SHA-256 去重保存；service_latest.log 使用带当地时间戳的 snapshot 名称，避免覆盖先前快照。
3. 不删除、不改写源文件；归档后重新核对目标 SHA-256，记录新增、去重和失败。
4. 读取 archive-run.ps1 输出的 daily_audit，检查本次新证据中的明显 WRONG_ROUTE；发现异常立即报告。
5. daily_audit.due=false 时仅归档；归档成功且没有明显 WRONG_ROUTE 等须报告异常时使用 DONT_NOTIFY。其他模块的既有告警不被此静默结果压制。
6. daily_audit.due=true 时继续第 8 节每日审计，不因为当前小时不是 09 而跳过；无法完成时明确失败或证据缺口，不伪造报告。

### 7.3 去重与完整性

文件级 SHA-256 用于识别相同内容和核验归档；同名轮转或 latest 快照不能覆盖旧证据。日报再做规范化记录级去重，以免多个快照包含相同日志时重复计数。去重应只消除同一证据的重复副本，不能压掉实际发生的重复错误；具体记录标识策略待验证。

源日志可能变化或轮转，必须保留实际复制和核验状态；出现不可读、缺失、核验失败或无法形成一致快照时报告缺口，不用计划成功代替实际结果。归档记录数不直接等于全天连接次数，也不等于流量字节数。

### 7.4 只读与秘密边界

归档／审计不修改 Clash、Profile、规则、节点、代理组、TUN、DNS、路由、防火墙、系统代理或订阅；不启动 Claude／浏览器、不连接 Claude、Anthropic、OpenAI、测试站或其他外部服务、不运行故障演练、不删除文件、不复制或输出认证材料。后台上报由独立职责执行，不借此让只读归档任务联网。[M0]

“原始归档”与“不复制认证材料”同时受约束。若源日志意外含代理用户名、密码、Cookie、Token、Authorization 等，不能原样写入普通 raw；应报告秘密材料异常并保留覆盖说明。若支持脱敏派生件，必须单独标记并计算自身哈希，不能冒充原始字节一致；具体例外保存方案列入安全实现待定。不为处理秘密而改写源文件。

## 8. 每日审计到期、窗口与幂等交付

### 8.1 时间与到期规则

所有日期目录、到期判断和用户可见审计时间按 America/Los_Angeles 的当地时间解释。使用时区规则与实际偏移，不将全年固定为某个 UTC 偏移；CurrentTimeIso 必须能明确对应实际时刻。其他时区支持尚未在本版锁定。[M0；U3]

每天当地 09:00 起到期。当天 daily-audit.md／daily-audit.json 未齐全或为空时，后续任意一次可用唤醒都应补做；不承诺 09:00 准点，也不得因当前小时是 11、13 或其他时间而跳过到期审计。

执行前再次检查当天报告是否齐全，防止同一轮重试或重复唤醒生成重复日报。两份完整有效非空报告已存在时，当天不重复；MONITORING_INCOMPLETE、FIXED_ROUTE_ERRORS、FAIL 等已交付结论同样计入，不能因非 PASS 而整天重跑。

### 8.2 部分文件与历史处理

仅一份有效报告存在时，优先读取已有报告补齐缺件，保持同一窗口、数据和结论；无法可靠恢复时报告失败，不覆盖有效内容。损坏、空文件或格式不可用必须明确标记；不因文件名存在就宣称交付完整。

不得删除或改写历史报告，不补造此前未实际运行日期的日报。今日已交付后出现的紧急事件另行即时记录和报告，进入后续审计窗口，不覆盖当天早先报告。需要追加解释时保留为独立关联说明，不替换原文。

### 8.3 审计窗口

若存在上一份完整有效的报告，window_start 取其 window_end；否则使用最近 24 小时。window_end 取本次审计确定的结束时刻，并在两种格式中保持一致。窗口采用左闭右开 [window_start, window_end)。

本轮产品增量明确：“成功报告”指生成完整有效，不要求路由结论是 PASS。上一份完整的 FAIL 或 MONITORING_INCOMPLETE 报告也推进窗口；覆盖空档仍在证据中保留，不因推进窗口就宣称已补齐。[U3]

日期目录表示报告所属当地日期，不保证窗口恰好等于该日 00:00—24:00。日报必须直接展示实际窗口；不能把跨日窗口用量称作单个自然日精确统计。

### 8.4 证据合并与回放

读取该窗口内已经归档的 raw 及当前可见源日志；按 SHA-256 和规范化记录去重后调用共用 replay-logs.ps1 回放。记录 window_start、window_end、source_files、SHA-256、唯一记录数、coverage、issues 与证据边界。

日志不可读、窗口不连续或源文件缺失时，coverage 标注 MONITORING_INCOMPLETE，不猜测流量损失或泄漏。空档可能是缺采或没有活动，仅凭日志空白无法区分；应用运行与采集状态要一起说明。

复用现行 archive-run.ps1 时，传入对应当地时间的 CurrentTimeIso，并确认输出 classification_version=2；新产品适配使用其明确登记的版本，不暗中替换旧 v2。现行脚本名称、参数和输出作为继承基线。移植后仍须一套分类口径；实际去重实现、日志语法兼容和损坏报告校验方式在开发中验证，不能临时由 AI 补算。

## 9. 统一日报结构、结论与示例

### 9.1 同一份日报的六部分

| 部分 | 必须包含 |
|---|---|
| 总览与范围 | 审计日期、时区、生成时间、窗口、用户／设备／环境引用、采用过的方案和版本、路由结论、覆盖状态 |
| 流量与额度 | 本机上传／下载、代理／直连、应用归属、A／B 分布与缺测；服务端月度总量、剩余、单位、重置与同步时间 |
| Claude 路由审计 | 相关唯一记录总数，四类计数，旧版本进程专项，实际解析与覆盖边界 |
| 异常与应急处置 | 事件首次／最后时间、进程、目标、命中规则、预期与所选出口；阻断、通知、上报、修复、复查、恢复结果 |
| 归档与证据 | 新增／去重／失败、快照、源文件及 SHA-256、核验结果、可用覆盖、空档和采集异常 |
| 诊断与待办 | 已确认事实、固定链健康问题、推断原因和待核验项、AI 使用状态、待用户或后台处理的事项 |

两种格式使用同一批结构化结果，不让 Markdown 的文字与 JSON 的计数、窗口和状态相互矛盾。明细在本地呈现；上报由第 10 节信息边界约束。

### 9.2 结论优先级与并列状态

| 条件 | 路由／审计呈现 |
|---|---|
| WRONG_ROUTE > 0 | FAIL，醒目列出异常；同时记当前是否已阻断或修复，修好不删除历史计数 |
| WRONG_ROUTE = 0，ROUTE_ERROR > 0 | FIXED_ROUTE_ERRORS，报告正确固定链的健康异常，不写成泄漏；现有保护继续 |
| 完整窗口可核验且没有路由错误或待判问题 | DAILY PASS，明确只针对本次可用证据和声明范围，不等于应用层成功或账号健康 |
| 日志／窗口／来源不完整 | MONITORING_INCOMPLETE 并解释缺口；已发现 FAIL 或 FIXED_ROUTE_ERRORS 同时保留 |
| 日报生成或补件失败 | 交付失败状态单列；不能把文件生成失败伪装成零异常或修改历史文件来掩盖 |

建议把 route_result、coverage_status、delivery_status、protection_status 分开记录，属于报告字段分工，不新增另一套控制系统。没有完整覆盖时不能只显示 DAILY PASS；四类计数只统计可判记录，解析不出的数量与原因也要呈现。

### 9.3 用户提供的单次归档样例

以下数字仅来自用户贴出的输出，未在本轮独立复核，不是新应用实测，不补写未知日期或两小时窗口。[M1]

| 指标 | 用户提供的值 |
|---|---:|
| 新增归档 | 7 份 |
| 去重 | 2 份 |
| 通过哈希核验 | 9 份 |
| 当前可见相关记录 | 1,247 条 |
| 错误出口 | 0 条 |
| 固定链路错误 | 36 条 |
| 当次日报 | 输出称尚未到当地 09:00，不生成 |

正确摘要：本次归档成功，当前可见记录中未发现错误出口，存在 36 条固定链路错误；每日审计尚未到期，待按完整窗口回放汇总。此结果不能升级为“今日全程安全”，也不能把 36 条错误写成 36 次泄漏。

PASS_ROUTE、SAFE_REJECT 的各自数量、流量字节和完整覆盖未在这段输出中给出，不能用减法或 AI 补造。日报根据唯一记录回放，不直接累加历次归档所见记录数；重复快照还须去重。

### 9.4 基本数据字段

| 数据对象 | 必需字段族 |
|---|---|
| 报告 | report_date、timezone、generated_at、window_start/end、设备／环境、配置与分类版本、结论、覆盖、交付状态 |
| 用量 | 来源、统计范围、区间、上传／下载、代理／直连、A／B、应用归属、缺测、单位、服务端额度快照与同步时间 |

| 应急事件 | 事件引用、严重等级、首次／最后、计数、授权来源、动作及各阶段时间、阻断确认、后台回执、修复与恢复 |

## 10. 界面、后台上报与信息保护

### 10.1 管家式界面

| 区域 | 用户应看到的内容 |
|---|---|
| 运行首页 | 当前方案、速率、用户额度、本机用量摘要、保护／采集状态、最近验证；不要求阅读原始日志 |
| 流量明细 | 本机应用、代理／直连、A／B 和时间分布；未识别和缺测范围明显可见 |
| 异常卡片 | 问题、证据、等级、已采取保护、当前影响、后台处理状态、建议动作与确认入口 |
| 事件详情 | 发现到恢复的时间线，规则与出口对比；指令发出与确认生效分开 |
| 日报与历史 | 阅读／导出 MD 和 JSON、实际窗口、覆盖缺口、路由结果、用量与处置；不提供改写旧结论入口 |
| 授权与诊断包 | 查看已授权监测／保护／上报范围，额外证据提交前预览和脱敏确认 |

正常项默认折叠，持续故障去重提醒。危急通知立即显示，不被归档 DONT_NOTIFY 或每日已交付状态吞掉。第四模块不另增风险分，需整体评估时调用 FD-02。

### 10.2 后台可见范围

默认上报应用用户／设备的必要引用、用量汇总、方案与分类版本、事件类型和严重度、保护与修复状态、必要故障代码及摘要。不默认上传完整域名访问历史、所有应用明细、原始日志或完整日报。

本地报告中的详细进程、目标域名和规则证据不因写入日报就自动上传。进一步排障时，用户授权提交必要的脱敏片段或诊断包。危急事件允许按首次授权立即上报最小必要事件，不等待用户逐条点击。

### 10.3 离线与消息结果

后台不可达时，客户端保护、归档与标准审计继续工作，事件在本地保留待报；通过已批准路径恢复联系后补报。发送尝试与后台确认分开记录。不得为发送告警而放开未知直连、切换 Claude 出口或绕过 FD-03 配额与服务限制。

重复传送同一事件须可识别，不变成多起事故；无法上报时用户仍看到本地通知和状态。具体通道、重试间隔、队列存储和容量在实现时确定。

### 10.4 日志与清理衔接

活动日志、当前审计窗口内证据、已生成日报不进入 FD-01 的普通默认清理清单。监控正在使用的文件不可因过去有删除记录就重复清理；历史清理台账明确只是历史，不是通用执行策略。[S1 §4、§7；S2 purpose]

归档／审计任务不执行保留期删除。长期容量、保留期限、用户主动清理和空间不足策略另行明确；若以后清除历史证据，应保留真实缺口，不伪称原始材料仍完整。已生成报告不得由新一轮审计改写或覆盖。

用户项目记录、项目记忆、项目配置继续受保护。普通日志、模型输入与导出不含代理用户名／密码、Cookie、Token、Authorization、私钥或其他认证材料；对意外秘密采用第 7.4 节例外边界，不靠“只读”声称没有敏感数据风险。

### 14.2 交付前应具备的证据

在已声明支持环境中验证危急触发、实际阻断、错误重连保护、后台离线与 AI 不可用情形；验证三方案按事件时间正确分类，错误路线与正确链路故障不混淆。

执行日志应证明归档／审计没有改网、发测试请求或删除文件；普通清理不误删监控证据；上报与导出没有秘密或未授权的访问明细。第 12 节为功能场景清单，数值指标在实现前补齐。

### 14.3 本板块完成定义

普通用户能够查看流量与方案状态；已确认关键保护异常时，客户端程序按预授权及时阻断并如实报告，后台处理托管原因，修复后通过真实复查恢复。应用持续保存可核验的只读证据，每日按到期规则生成包含流量使用、Claude 出口审计与应急处置的统一双格式报告，明确窗口、覆盖和未完成项。

**最终承诺：紧急事件不等日报，保护不等 AI 或后台，日报不改写历史；采集有范围、分类有依据、用量有来源、动作有授权、恢复有验证。不是用无日志代表无风险，也不是把只读归档脚本变成无限权限的修复代理。**
