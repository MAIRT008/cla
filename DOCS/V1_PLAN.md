# Claude 环境管理应用：完整首版方案

> v1.3 · 优化修订稿。四模块业务要求保留；复用路线按实际适配成本选择。文档修订不代表候选集成或产品功能已通过，产品仍 UNVERIFIED。

## 1. 用户最终使用什么

首页呈现环境健康、当前方案、保护状态、本月代理用量，以及一个“开始扫描”按钮。首次获 AI 数据授权后进行深度扫描；后续默认快速体检。结果页给出危急、重要、轻度问题、依据、建议处理、影响和恢复范围。用户可以取消项目，一次确认后自动处理并复查。

侧边只需要“环境体检、网络方案、流量与日报、设置”。清理和网络结果在同一问题清单衔接，不让用户搬运配置。账号是否正常由用户回答；没有聊天窗口，也不要求普通用户填写代理或模型参数。

管理员端维护应用用户、资源分配、方案版本、共享资源余量、个人额度、模型服务和最小异常事件。用户登录的是本应用，不收集其 Claude 密码、Token 或完整对话。

## 2. AI 精确清理怎样真正工作

对应 FD-01/F01—F28、FD-02/N20—N28。

1. 客户端发现实际 Desktop、Code、默认浏览器/Profile、关联第三方和项目保护对象，形成带版本、定位和内容指纹的事实。
2. 用户确认已识别账号是“正常”还是“受限”。身份无法可靠关联时不把未知账号当受限。
3. 客户端加载本地提示词和工具说明，按 AI 数据授权把必要的脱敏摘要发到本应用服务器。服务器持有模型端点、密钥和模型参数，完成模型调用。
4. AI 可以请求进一步的受限读取，例如指定配置字段、已发现目录的有限列表、引用关系。客户端只在本次扫描范围内执行，秘密字段只返回类型和存在性，不传值。
5. AI 生成精确处理计划：对象、字段或记录、原因、预期变化、影响、保留项、备份方式。它负责判断和排序，不是把所有文件名交给用户判断。
6. 用户确认计划后，AI 调用一次本地“执行已确认清单”工具；程序在这次批量任务内逐项检查、备份、执行和复查，再返回汇总回执。无需每个文件都等待新一轮模型指令。相同操作标识重复请求不重复删改；目标变化、占用、权限不足时暂停对应项，其余独立项目可继续。扩大对象或动作仍需新计划和确认。
7. 修改先生成本地恢复材料；执行后重新读取实际字段/记录与保护对象，出具成功、部分成功、跳过或失败。AI 解释剩余问题，评分仍由固定规则计算。

执行工具不提供任意 PowerShell/命令字符串。受支持动作包括文件删除、JSON 字段修订、支持数据库中的明确记录处理、站点范围操作、配置恢复。模型可以编排工具，不能用自然语言绕过项目保护和用户确认。浏览器站点数据若只能整站清理，必须显示真实影响；不能把整站删除标成仅删除一个受限账号。

建议首批样例复用历史中的“纯第三方文件可删除、混合文件只改字段、正常 OAuth 保留、CC Switch 只处理选中记录、浏览器单站点范围、含项目资料的备份保留”六组。全部替换为合成身份和测试目录，不在 Owner 当前账号上做删除试验。

## 3. 网络与默认浏览器

对应 FD-02/N01—N34、FD-03/F13—F28。

网络事实分三层呈现：配置期待什么、内核当前加载什么、实际请求经过哪里。时区、语言、DNS、IPv6、WebRTC、IP 来源与信誉信息分别注明测量方式。分数衡量已声明检测规则，不解释为账号安全概率。

初始评分表、根因去重、关键缺测和基础路由优先级见 [评分与路由提案](SCORING_AND_ROUTING.md)，使用独立网络规则版本，经 P5 样例校准后采用。

默认浏览器由操作系统登记发现；有多个 Profile 才让用户简单选择当前使用项。桌面能准确读取的先读；浏览器内信号通过用户主动打开的一次性诊断页回传，绑定本次会话和实际浏览器。不能用新的空 Profile 或应用 WebView 的结果代替。

“Claude 专用配置”建议先采用用户现有浏览器的专用使用约定和受支持设置：把选定浏览器进程纳入 Claude 固定 A，调整用户确认的语言、WebRTC/安全 DNS 等明确可改项；系统时区等影响全机的设置单独显示影响。浏览器不能局部实现某项时给出手动步骤，不强制安装指纹浏览器，不伪造浏览器指纹。

首版不承诺按标签页精准分流。同一浏览器进程里的其他网站也可能跟随 A，界面需要在专用配置确认页明说。真实浏览器检测结果和路由归属都保留该限制。

## 4. 三套方案、故障保护与应急上网

| 方案 | Claude 受保护连接 | 其他公网 | 日常白名单 |
|---|---|---|---|
| 日常单 IP | 固定 A | 白名单直连，其余 A | 启用，Claude 规则优先 |
| Claude 专用单 IP | 固定 A、TUN 接管 | A | 保留但不生效 |
| Claude 专用双 IP | 固定 A、TUN 接管 | B | 保留但不生效 |

A 是同一用户三方案的 Claude 固定出口。双 IP 按用途分工，不轮换；前置节点可更新不代表 A 可以改变。固定与独享分别记录。必要回环、局域网、代理链建立通信由模板明确，不使用宽泛 DIRECT 兜底。

沿用现行方案的“固定链失败则连接失败”逻辑；同时验证内核退出、TUN 失效和新连接时保护仍然有效。普通 UI 关闭不应解除保护。客户端程序执行紧急阻断，AI、后台、两小时归档和日报均不在第一响应依赖链上。

**手动应急上网**：用户点“临时上网/联系支持”，确认后仅开放独立应急通道；Claude 及专用浏览器继续受原保护。有合适的已安装第二浏览器时，优先验证其可区分进程路径和既有路由；没有时，再验证应用现有 WebView 或其他明确范围的路径。不能把受保护的同一个 Chrome 进程切到应急出口。只有支持站点可用不代表普通应急上网已完成。应急资源是否可用、到期及恢复条件单独显示，结束后关闭通道并复查原方案。

应急通道也不能绕过该用户已耗尽的托管额度。额度耗尽时只允许显式批准的支持站点访问方式或单独分配的有限支持资源；普通应急上网仍需要有效资源。完整流程见 [运行行为](RUNTIME_BEHAVIOR.md)。

## 5. 共享订阅与按用户停止

对应 FD-03/F01—F12、F29—F36；这是已确认的硬要求。

多个应用用户共用上游资源池，池可能总计 500 GB；每用户有自己的额度，例如 250 GB。A 用户达到自己的上限，只停用 A 用户在全部已分配线路的服务身份，B/C 用户继续使用。资源池先耗尽是供应异常，不能写成某用户超额。

**先选有独立用户计量与停用能力的现成服务接口。** 如果当前共享订阅只有一份共用凭据、一个总字节计数，则需要一个可控接入节点提供独立用户身份。建议候选是成熟用户配额管理组件及其流量节点，不自研计量平台。

可验证的候选链路是：本机 Mihomo → 独立用户身份的受管接入节点 → 共享上游前置 → 用户固定 A/B → 目标。全部托管流量经过同一个确定的用户计量点；客户端不拿到可以直接绕过该节点的共享上游凭据。后台管理应用负责配置和读取该计量权威，管理进程本身不一定转发流量。

这条候选链路会改变物理连接路径。供应商原生子账号能满足时不用额外节点；不能满足时，先列清每段协议、凭据持有方、服务端 A/B 分流和同一用户账目如何合并，再用一个用户实测全链，随后验证三用户独立停用。只让一个成熟节点候选先进入验证，有明确缺口才测试备选；不能把“能装面板”当成接入完成。

仅停止订阅更新链接不足以停止已缓存节点或已建立连接。服务端必须拒绝该身份的新连接，并处理在途连接；所有 A/B 路径纳入，其他用户不受影响。客户端计数用于展示，不能修改后台账目。重装、改电脑时间、切换方案、恢复旧配置均不重置或绕过额度。

建议结算参数及验收边界见 [待定决策](OPEN_DECISIONS.md)。不要求用户进一步解释这个业务目标；下一步需要的是供应商或受管节点的实测结果。

## 6. 流量和 AI 每日报告

对应 FD-04/F01—F44。

首页显示本机当前速率/累计量、服务端本月已用/总额与同步时间；两者统计范围不同，不能硬凑相等。展开显示 A/B 路线、可辨认的进程和未知部分。A 路线上的全部流量不自动等同于 Claude 实际使用量。短连接未采集到就标缺口，不新建全流量解析系统。

复用已经读取的归档、回放和 route-classifier 基线。旧 classification_version=2 保持个人历史语义；产品新版本按事件时用户和 A/B 映射分类。日志计数与字节来源分开，不能把日志条数换算为流量。

每两小时只读归档；America/Los_Angeles 09:00 后首个可用唤醒生成到期日报。窗口接上一份完整有效报告的结束时间，否则取最近 24 小时。MD/JSON 从同一结果生成，FAIL 和监控不足也算交付。路由结果、覆盖、交付和当前保护状态并列，错误不会因缺测消失。

标准日报先本地交付。独立的 AI 分析任务经既有数据授权，将脱敏汇总通过本应用服务器调用模型，返回原因和待办；AI 失败保留标准日报。迟到分析保存为带原报告引用的独立附注，不改写已交付历史计数。归档和标准回放本身仍不联网、不改网、不发测试流量。

## 7. 最小实现结构

桌面只比较“Clash Verge Rev 裁剪复用”和“轻量新壳复用 Mihomo/既有采集”两条路线，暂不指定 Wails 或 CVR 胜出。用相同的受管配置应用、回读、退出和恢复场景比较净改造量，再固定语言和目录。若采用 CVR，收窄其原配置生成链，避免在原管理器旁增加第二个配置写入者。网络服务可复用上游适用实现，不要求另外新建一个同职责服务。

AI 比较“现成模型 SDK + 小型受限工具循环”与 Pi Agent 层，以本地调用、取消、恢复和服务器模型配置适配的实际代码量选择。不为 SDK 增加第二个 AI 后台。一个管理后台承接用户、配置、配额适配和模型调用；SQLite 可保存本地结果，后台单实例数据库够首版，配额真实账目仍只有服务节点权威。固定候选版本、比较场景和采用条件见 [复用计划](REUSE_PLAN.md)。

不按四模块各建服务、配置副本、计量账或 Agent。评分、分类、配置发布与本地执行分别有一个共享实现。AI 不承担循环轮询、计数和断流检测。

## 8. 交付和开发顺序

先收口复用候选和供应商能力，再做会改变采用决定的小验证。2—3 个有效工作日是资源就绪时的首轮试验时间盒，不保证这段时间内完成全部技术证明。桌面/AI 路线有证据后，本地清理、界面和合成样例可推进；资源接入、配额和网络保护沿各自依赖验证，尽早联调。验证资产继续接入产品，不完成样机后全部重写；四模块的最终验收保持完整。

Owner 已指定 GROK 与 Codex 5.3 共同施工，当前验收 Agent（本任务）负责独立验收和技术裁决。原功能内测 4—6 周、完整 V1 试用 6—8 周保留为旧施工假设下的参考；开工时根据两方具体分工和选型证据校正，不因使用两名 Agent 就自动减半。采用决定形成后删除已被复用覆盖的工作、加入实际适配与验证成本，外部等待单列。数值目标先观察成熟方案表现再确定，不能作为未经评审的淘汰门槛。详见 [开发计划](IMPLEMENTATION_PLAN.md)。
